Why this page exists

Over one conversation I gave three different answers to the same question about how the agent reads a page. Each answer was based on a number I had not fully checked. This page exists to end that, so it is written for someone with no background in the project and every claim carries the code that backs it.

The four questions this page answers, and the short answer to each
#QuestionShort answer
1What do Shopee and Lazada look like to an agent?Shopee announces a sold out size properly. Lazada announces nothing at all, and to an agent its whole size selector is one line of plain text
2What does our shop look like, and does it match them?It matches Shopee closely and Lazada not at all. It is the generous case, and that is a stated limit rather than a flaw
3Does openJiuwen really read the page, or only a summary?It reads the page. The claim is true. The summary it prefers is itself built by reading the page. The problem is what the summary throws away and never mentions
4How does the second agent differ?It reads the visible text of the whole page. No summary, no filtering, and it sees more of the shop as a result

1. The three ways to look at a page

A web page can be handed to a language model in several shapes. Understanding the difference between them is most of this page, so here they are in plain terms.

What each one is, without jargon
NameWhat it actually isRough analogy
Raw HTMLThe file the server sent, including every style rule, script and hidden attributeThe full printing plates for a newspaper, ink specifications included
Accessibility treeWhat a screen reader would announce. Only the meaningful parts, each labelled by what it is: a button, a link, a dropdown, an option, and whether it is disabledSomeone reading the newspaper aloud to you, saying "headline", "photo caption", "advert"
Card probe summaryopenJiuwen's own tool. It runs a small program inside the page, finds repeated blocks that look like product cards, and returns them as a listAsking an assistant to skim the paper and write out just the classified ads

The important point, and the one that took longest to establish: the card probe is not an alternative to reading the page. It is a way of reading the page. It reads the same source as everything else and then compresses what it found.

Code evidence that the probe reads the page

The probe is JavaScript that openJiuwen sends into the browser to run inside the page. These four lines are the ones that do the reading. Line numbers are from the file as it stands in the repository today.

What each of those lines means
LineIn plain terms
160Read the accessibility role of an element, which is the thing the accessibility tree is built out of
203Ask the live page for every element matching a pattern. This is reading the page directly
277Check whether something is switched off. aria-disabled is an accessibility attribute, so the probe reads accessibility information too
293Take the visible text out of an element

So the summary is built from the page and from accessibility attributes. Anyone saying openJiuwen "uses a summary instead of the page" is wrong, and I was that person for part of one afternoon.

What each one costs, measured on the same page

Measured on our shop's search page for the clothing market, fifteen products, window 1200 by 701. Each figure is the actual size of what would be sent to the model. Tokens are the unit models are billed in, roughly four characters each. Nothing here involved paying a model, the page was simply read four ways.

The same search page, four ways of looking at it
Way of lookingCharactersApprox tokensProducts it shows
Accessibility tree11,3942,84815 of 15
Card probe, as shipped31,7017,9254 of 15
Card probe, with the window limit switched off88,82222,20515 of 15
Raw HTML252,84863,21215 of 15

Read that middle row twice. The summary the agent is told to prefer is nearly three times bigger than the accessibility tree and shows a quarter as many products. It is not a saving. It is more expensive and less complete, at the same time.

How this was measured: openJiuwen's own probe code was loaded straight from its repository and run against our shop through a browser, once with its shipped setting and once with the window limit switched off, changing nothing else. The script is kept out of the repository because it is a one-off, and the numbers above are its output. No model was called, so this cost nothing.

Why the summary is so large

A quarter of it, 9,095 characters across 129 fields, is addresses describing where each element sits. One real example, sent to the model as part of the reply:

280 characters to say where one thing is. That is useful if the agent must click that exact element later, which is the case when filling in a form. It is wasted on fifteen products that the agent reaches by clicking an ordinary link.

2. What Shopee, Lazada and TikTok look like to an agent

All three were read by hand in September as an ordinary shopper, which is the only way this project is allowed to touch a live shop. The saved pages are not kept in the repository because they contain login identifiers. To get the accessibility tree without going near the live site, the size selector was cut out of the saved page into a small standalone file and read offline with all network access blocked.

Shopee, a water listing with two sizes sold out

The page's own markup. The two sold out sizes carry aria-disabled="true":

And the accessibility tree that produces, generated offline from that fragment:

This is close to ideal for an agent. Every size is announced, each is a proper button, and the two that cannot be bought say so in a way any tool can read.

The prices are a different story. Shopee ships a block of data inside the page listing all four sizes, and every one of them has "price": null. The listing publishes a range, 11.90 to 19.90, and never says which size is which. So on Shopee availability is disclosed and price is withheld.

Lazada, a clothing listing with one size unavailable

The markup. There is no button, no role and no accessibility attribute. The only signal is the word "disabled" inside a class name, which is styling information:

And the accessibility tree that produces:

One line of plain text. Not a list, not buttons, nothing marked unavailable. An agent reading the accessibility tree of a Lazada size selector cannot tell that anything is out of stock, cannot tell where one size ends and the next begins, and has nothing it can obviously click.

Lazada also publishes no price at all in its structured data, and its internal data block carries no price for any size. Its stock flag is "disable": false, which appeared 50 times and never once as true, so unavailable combinations seem to be left out rather than marked.

TikTok Shop, which withholds nothing

TikTok embeds a complete table in the page before any interaction. Each entry has its own price and its own live stock count:

Twenty six entries, each with a price and a quantity, all present on load. TikTok Shop does not gate variant information at all.

The three marketplaces side by side
ShopPrice of each sizeStock of each sizeHow an agent would know something is sold out
ShopeeWithheld until you clickPublishedCleanly. [disabled] on a proper button
LazadaWithheld entirely, no price anywhereNot published as a flagIt would not. Only a styling class name says so
TikTok ShopAll published on loadAll published on loadDirectly from the data, no interaction needed

There is no standard here. Three shops, three completely different answers. That is itself the finding for the first research question, and it is why the project builds a retrieval policy rather than a parser for one site's layout.

The honest summary: our shop is a faithful copy of the Shopee case and a poor copy of the Lazada case. Everything measured in this project is therefore a lower bound on how bad the problem is in the wild.

4. One question, start to finish, from a real run

This is an actual recorded run, not a description of how it might go. The question was "which seller is cheapest for the 2 x 9.5L pack", asked against a market of fifteen sellers. Sixteen steps. Every line below came out of the run's own log.

Run scaled-cheapest-target-2, 9 September 2026
StepTool usedWhat happened, and what the agent could see afterwards
1browser_navigateGoes to the search page. The reply contains no page content. It gives the address, the title, and a filename where a full snapshot was saved. The agent is told a snapshot exists and is not given it
2browser_probe_cardsAsks for the card summary. Reply is 26,469 characters, says 'viewport_only': True and 'total_candidates': 4, and names four sellers. Eleven more exist further down the page and the reply does not mention them
3browser_clickClicks into the first of those four
5browser_snapshotOn the product page, asks for the accessibility tree. 9,528 characters. This is where the sizes appear
6 to 12navigate, snapshotBack to the search page, into three more products, tree read on each
13, 15browser_take_screenshotTwo pictures taken, late, after the reading was done
16browser_evaluateA small calculation, then the answer

Four products opened out of fifteen. The four it opened are the four the summary named.

What the product page looked like at step 5

This is the accessibility tree the agent received, copied from the run's log. Note that this run predates the price suppressing theme, so the prices are visible:

Every size and its extra cost, sitting in the reply, with nothing clicked. The agent could add 6.82 and 10.86 and report 17.68 without ever selecting the size. That is the price leak this project found on 18 September, and it is why the suppressing theme exists. Under that theme the same menu now reads option "2 x 9.5L" with no figure attached, and the price appears only after the size is chosen.

What the summary does not carry

Running the same card probe against a product page rather than a search page, on a listing with two sold out sizes, the reply is 18,253 characters and the word "disabled" appears zero times. The size menu is not in the summary at all. The accessibility tree of the same page is 4,499 characters and carries the whole menu with both sold out sizes marked.

So on a product page the summary is four times larger than the accessibility tree and is missing the one thing the question needs. The agent does read the tree on product pages, which is why this has not caused a measured failure. It is a trap waiting rather than a trap sprung.

5. The Huawei claim, tested line by line

The claim comes from a developer talk deck, OpenJiuwen Web & Coding Agent.pptx, slide 5. Not from the published paper: the paper is about coding agents and contains no instance of the words browser, DOM, accessibility, screenshot or Playwright, which was checked by searching its text.

Slide 5: "Agent reads the control tree (DOM + AX) by default & adds screenshots only when the page is ambiguous"
Each part of the claim against what the code does
The claimWhat was foundVerdict
Reads the page structure rather than picturesAcross 360 recorded runs: 1,656 accessibility tree reads, 1,560 page searches, 421 card summaries, and only 277 screenshots. Roughly thirteen structural reads for every pictureTRUE
Uses DOM and accessibility informationThe card summary is JavaScript run inside the page. It calls document.querySelectorAll at line 203, reads aria-disabled at line 277 and role at line 160. The snapshot tool returns the accessibility tree directlyTRUE
Screenshots only when the page is ambiguousScreenshots are rare and, in the run traced above, taken late and after the reading was done rather than in place of itCONSISTENT
By defaultThis is where it gets complicated. Navigating gives the agent a filename, not the page. The shipped prompt tells it to prefer the compact summary. So the default first look at a page is the summary, and the summary is limited to the visible windowTRUE BUT INCOMPLETE

The claim is not false. I want to be plain about that, because the opposite would be an accusation against a real team and the evidence does not support it. They say they read the page and they do read the page.

What is actually wrong, stated precisely

Three facts that compose into the problem, each with its source
#FactWhere it comes from
1The shipped prompt tells the agent to use the card summary first on any page with repeated listings, and to use that summary as its evidence instead of taking snapshotsagents.py lines 184 to 196. The exact words: "prefer browser_probe_cards first" and "use that compact result as the evidence for extraction and final reporting instead of taking screenshots, snapshots, or running extra DOM scans"
2That summary throws away anything below the fold of the windowprobes.py lines 190 to 195. The test is if (rect.top > window.innerHeight) return false;. Our cards start at 671 pixels down and the second row starts at 1128, in a window 701 tall, so the second row onwards is discarded
3The reply never says anything was thrown awayChecked directly in the probe output. There is no field naming a skipped or off screen count. It reports what it returned and stops

Put together: the agent is told to use a tool, the tool silently discards most of the page, and the agent has no way to know. It is not being lazy and it is not ignoring the page. It asked a fair question and got an answer with no hole in it.

Does this actually cause the behaviour

The strongest available evidence, from walking every recorded run step by step and noting which page the browser was on for each observation. Split by experimental arm first, because several arms were explicitly told to open more listings and mixing them in would answer the wrong question.

Every openJiuwen run that opened at least one listing, 307 in total, grouped by what the agent was told

Read the first row only, since it is the one with nothing added. Of 74 unmodified runs that opened exactly four listings, not one of them ever read the search page in full. Of the 38 unmodified runs that opened some other number, 30 did. Zero out of 74 against 30 out of 38.

The other rows are not noise, they are the confound. "Told to open everything" never stops at four, and all 19 of its runs read the search page, which is what being told to look properly does. An earlier version of this page quoted 2 of 101 against 84 of 94, pooling every arm together. That number was not wrong arithmetic, it was the wrong population: it mixed agents that were told to look harder with agents that were told nothing. Splitting by arm makes the pattern cleaner rather than weaker, and pooling was the mistake.

They span four markets, two products, both models and both settings of the shop, which is why the pattern is not a property of one market. Note the last two rows, the clothing market seeded on 18 September: 19 of 22 runs there opened exactly four, on a page where all fifteen products render at once with no page turning involved.

What this does not prove. This is a pattern across recorded runs, not a controlled experiment. A model inclined to look less might both skip the tree and stop early for reasons of its own. The test that settles it is to switch the window limit off, change nothing else, and see whether runs still stop at four. That change has been verified to work at the tool level, shown below, and has not yet been run with a model.

openJiuwen's own probe code, run against our shop, one setting changed

The fix works and costs about three times as much as the broken version. The accessibility tree shows the same fifteen for 11,394 characters, which is an eighth of the cost of the fixed summary. On this kind of page the best available option is the one the prompt steers away from.

The smallest useful change upstream would be for the summary to report how many candidates it discarded. One number. The tool already has the full list in hand before it filters. That would let any agent notice there is more to see, without changing any behaviour by itself.

6. The second agent, and why it exists

If every failure came from one agent, the failure might belong to that agent rather than to agents in general. So a second one was written from scratch, deliberately plain, in experiments/naive_agent.py. It has four tools: go to a web address, read the page, choose an option in a dropdown, and answer.

How the two differ
PropertyopenJiuwenThe plain loop
What it sees on arrivalA filename. It must then ask for somethingThe page text straight away, every time
Window limitYes, on the summary, on by defaultNone. It reads the whole page regardless of what is on screen
Advice about how much to lookDetailed. Prefer the summary, avoid extra scansNone at all, which is the point
Sold out sizesVisible in the accessibility tree as [disabled]Visible as [unavailable], added 18 September

That last row was a defect found this week. The plain loop originally read the page with innerText, which prints a disabled option exactly like an available one, so it could not have answered a stock question at all while openJiuwen could. The two agents would not have been answering the same question, and the difference would have been recorded as a difference between agents. It now emits a short block naming each menu and marking what cannot be chosen:

The first result from this second agent already changed a conclusion. It opens fewer listings than openJiuwen does, not more, which was the opposite of the recorded prediction. So "agents read the first screen and stop" is not simply a quirk of one tool's default setting.
