Ambiguity Without Adversary

Shopping agents answer questions about prices they never looked at. Nobody set a trap. This project measures how often that happens and builds a retrieval policy that decides what to gather before answering.

All three research questions now have measurements. The contribution, a policy that reads the question and decides what to retrieve before opening anything, matches the expensive baseline on accuracy for roughly half the interactions, on a market it was never developed against.

1. The failure this project is about

Observed by hand on a live marketplace in August 2026, as an ordinary shopper. No automated traffic was ever sent to a commercial site.

A deployed shopping assistant was asked for the cheapest 2 x 9.5L carton of a named brand of water. It named a seller, gave a price, and computed a cost per litre to justify the choice. It was wrong. The price it quoted belongs to a different pack size, and a cheaper seller existed for the size actually asked about.

What the assistant said against what the listings actually charge
SellerPrice shown firstPrice for 2 x 9.5LWhat the assistant did
BenWholesale$10.20$17.90Named as the cheapest at $10.20. That figure is the 6 x 1.25L pack, not the pack asked about
Shopee Supermarket$15.50$15.50Actually the cheapest for the size asked about, and never mentioned

Three things make this the right problem to study. The answer was confident and carried no uncertainty marker. The arithmetic was correct and the attribution was not. And no merchant did anything deceptive, which is why the title says ambiguity without adversary. Injection defences look for an attacker. There is no attacker here.

Two of three marketplaces withhold the price of a variant until it is chosen, and the two that withhold it disagree about everything else: one announces unavailability to a screen reader, the other says it in a class name a screen reader never sees. Gating is a pattern with no standard, which is what makes a retrieval policy the right unit of work rather than a parser.

Three consequences worth stating plainly. A published lower bound is not something the method may assume, because one marketplace of three publishes one and another publishes no price at all, so the bound keeps being parsed from the rendered card. Gating at the listing level holds on all three and on the test shop, since a search page shows one price per card whatever the platform does inside a listing, and that is where every failure measured in this project lands. And the default test shop is not a broken shop: publishing every variant price on load is exactly what TikTok Shop does today, so the two themes are two real regimes rather than a fault and its fix. Both are now measurable on demand, and a run records which one it met.

The last row is different in kind, not in degree, and it sets a boundary on what the method can claim.

a "from" price is a valid lower bound   →   the listing can be skipped safely a "from" price minus an unknown voucher   →   the bound is unsound and the winner could be skipped

Selecting a size is reversible and local. A cart is global and persistent, so retrieving an answer changes the state that later retrievals happen in, and an exploratory add to cart has to be undone rather than navigated away from. Any policy that treats retrieval as free observation is wrong there. The pruning result on this page therefore holds in the absence of voucher pricing, which is an explicit scope boundary rather than an unexamined assumption.

3. How a web agent reads a page, and why that matters here

An agent does not see a web page. It receives one of three representations of it, and the published designs all offer the same three.

The three representations, and what each one holds on a gated listing
RepresentationWhat it isOn a gated listing
Page sourceThe markup the browser receivedHolds the selected size's price only, on the live marketplace
Accessibility treeThe structure a screen reader would announceA subset of the page source, so it can never hold a price the source lacks
ScreenshotA picture of the visible windowShows the selected size's price, the same as the others

All three agree with each other, so there is no contradiction for an ambiguity check to detect. The information is missing rather than conflicting. That is why adding vision does not help, and it is why the fix has to be about retrieval rather than about perception.

5. Where this sits in the literature

Plenty of work tries to make a model admit when it is unsure. Each line rests on an assumption this failure breaks. In one line: abstention research asks whether a model knows that it does not know. This asks whether an agent knows that it did not look.

How the project got here

The registered title names injection defences because that is where the work started. The closest earlier work runs prompt injection against web agents in the same WebArena shop this project uses, with deployed agents rather than prototypes, and reports attacks succeeding between 41.67 and 68.59 per cent of the time.

The pivot came from one observation about that paper. Its most interesting finding is that an attack on the user often succeeds while the delegated task still completes, so nothing looks wrong from the outside. That is a statement about detectability rather than about attackers, and the same invisibility arises with no attacker at all. On a gated listing the agent reports a price, the task completes, and the answer is wrong. Remove the adversary and both the failure and the invisibility remain, which is what suggested the adversary was never the load bearing part. There is a defensive argument too. Injection defences work by filtering what enters the agent's context, and a perfect filter cannot help when nothing harmful entered. The defect is an absence, and absences do not arrive to be filtered.

What this project claims that is not already claimed

Three claims, kept narrow enough to defend
#ClaimWhy it is not covered by the above
1A failure class defined by absence rather than errorEvery observation is correct and the answer is still wrong. Uncertainty over a given context cannot see it, because the defect is in what was never observed
2A sufficiency check grounded in the action record, not in confidenceNeeds no model internals, no second model call and no training, so it costs nothing and works through a black box interface. It withdraws 29 of 31 wrong answers across 125 runs on three markets
3Soundness reported separately from correctnessOn one question the agent opens exactly four listings of fifteen in every run, so its one right answer rests on the same evidence as its wrong ones. An accuracy-only evaluation cannot tell those apart

10. Why the agent stops at four listings

This is the mechanism behind the whole RQ2 result, and it is a design choice in the agent rather than a mistake by the model.

Three facts that compose into the failure
#FactSource
1The agent's own prompt tells it to use the smallest probe available and to stop once it has the fields it needsThe shipped system prompt, unmodified
2The card probe reads the visible window only, by defaultThe tool's own default setting
3At the window size used, one row of four cards is visible, and the probe reports total_candidates: 4Measured. Nothing in that reply says eleven more listings exist

The agent is not being lazy. It asks a reasonable question, gets an answer that looks complete, and has no signal that it is looking at four listings out of fifteen.

Until 18 September the shop itself accounted for part of that gap. Magento paginates at twelve by default, so three of the fifteen listings were on a second page and no amount of looking would have found them in one read. The page size is now 36, measured at Items 1-15 of 15, and the cards were measured again in a 1200 by 701 window: fifteen in the document, four intersecting the viewport, the second row starting 427 pixels below the fold. The whole of the loss now sits in the agent rather than partly in the shop, which is what makes the number worth quoting.

What the agent is advertised to do, against what it does

The reason this is a design choice and not an accident is that the design is published. openJiuwen's browser agent was presented at a developer talk, and the deck states the observation policy directly.

Three claims from the openJiuwen Web and Coding Agent deck, and the shipped code that answers each one
What the deck saysWhat the code doesWhere
"Agent reads the control tree (DOM + AX) by default and adds screenshots only when the page is ambiguous"After a navigation the control tree is written to a file and the model receives a link to it. The tree enters the context only if the agent spends a separate call on it, and the shipped prompt tells it to prefer the compact probes insteadSlide 5, against agents.py line 223
"Rule of thumb: structure first as it is cheaper, local screenshots only when info is missing"The structure channel is the card probe, and the card probe is bounded by the viewport. What is missing is therefore invisible to the rule that is supposed to detect missing informationSlide 6, against probes.py lines 190 to 195
"Object alignment and fusion. Structure versus pixels: consistent? Do not act on unresolved conflicts"The safeguard cannot fire here. The eleven unread listings are not a disagreement between structure and pixels. They are absent from both, and an absence raises no conflictSlide 6
"Layer 1, current page, latest snapshot only, overwritten when the page changes. Layer 4, every snapshot and tool call saved to disk but never sent to the model by default"Matches exactly. The context processor keeps the last observation and trims earlier ones to a thousand characters, and the snapshot files do sit on disk unreadSlide 8, against browser_agent.py lines 451 to 470

The compact probe is the compressed DOM and accessibility representation the deck describes, so the gap is not that the agent ignores the control tree. The gap is that the compression is bounded by the viewport and says nothing about what it dropped. A reply carrying total_candidates: 4 on a page holding fifteen is not wrong, it is silent.

Three limits on how far this is pushed. The deck is a promotional talk rather than a peer reviewed paper and is cited as a talk. It may describe an internal system of which the open source agent-core is a subset, and the repository documentation makes no observation claim at all, saying only that the prompt prefers compact probes over snapshots. The harness paper, arXiv 2608.27969, is not the source and has nothing to say here: it contains no instance of the words browser, DOM, accessibility, screenshot or Playwright. The project's working notes had recorded the control tree description as "the published architecture", which invited exactly that misreading, and the correction is recorded in appendix J.

What happens when the variant gate is actually closed

The shop was handing the browser every variant price on load, and writing each surcharge into the option label, so a price this project calls gated could be read without interacting. On 18 September a theme that suppresses both was added, selected by the browser's user agent so that ordinary browsing, and every run already recorded, render exactly as before. Same products, same prices, same answers, same URLs.

The gate now behaves like a gate. Selection goes from none to two thirds of runs, where across 122 recorded runs on these markets the agent had selected a pack size twice in total. It costs 64 per cent more and buys nothing: accuracy moves from 3 of 12 to 2 of 12, which at twelve runs is noise.

Coverage still separates the verdicts, and separates them identically in both arms. Every right answer opened 12 to 15 listings and every wrong answer opened exactly 4. Closing the gate inside a listing changed how the agent works and left what decides correctness untouched. That is the two layer reading measured rather than argued, and it is why the results on this page are about the gate between the search page and the listings.

11. RQ3, the retrieval policy

Two halves, built in order. The first knows when it has looked enough. The second knows where to look so that enough costs less.

Half two, a strategy chosen from the question before anything is opened

Three strategies, because three kinds of question need different work. The choice is made by reading the question text, never the task name
StrategyQuestion sounds likeWhat it allows the agent to skip
Total bound"which seller is cheapest"Any listing already advertising more than the best total found so far, because nothing inside a listing costs less than its advertised price
Refutation"does every seller stock it"Everything, the moment one listing is found that lacks it. One counterexample settles a claim about all fifteen
Rate bound"best value per litre"Any listing whose advertised price spread over the largest pack still loses to the best rate found. A weaker bound, and a real one

The strategy text is appended to the question and the agent's own system prompt is untouched, so the only difference between the plain version and this one is the words in the task. Two corrections were needed and both are recorded. Version one never enumerated the market before skipping within it, which is not pruning but ignoring. Version two followed the refutation instruction to the letter and surveyed ten listings when the first counterexample had already settled the question.

M. A second scaffold, and a prediction that failed

Every failure on this page was produced by one agent, whose card probe reads the visible window and reports four candidates where there are fifteen. That could be a fact about agents or a fact about that probe. The control is an agent with no probe at all: a loop written from scratch with four tools, go to a URL, read the page, choose an option, answer, and no advice about how much to look. Same model, same step budget, same viewport, same scoring and the same coverage counter.

The same four gated questions on the held-out market
ScaffoldRunsRightRefusedWrongListings openedActionsCost/run
openJiuwen123096.510.2$0.137

The prediction, written down before the run, was that a loop with no probe would under-retrieve less. It under-retrieves more. It spends its actions re-searching, sorting by price, sorting by name, paging and rephrasing the query, and opens two to four listings while taking twenty-one actions.

So the four card ceiling is not what makes the agent stop early. A scaffold with no ceiling at all stops sooner, for six times the money. The probe both causes the ceiling and carries the agent further through the market than a bare loop manages. That puts the failure in the model's judgement about when it has looked enough rather than in one agent's default, which is a broader claim than this phase set out to test.
