Ambiguity Without Adversary

A shopping agent answers from the page it can see. When the price, size or stock a question needs only appears after a click, the agent often answers anyway, confidently and wrongly. This project builds a box that reads the question first, decides what must be opened before an answer can be trusted, and asks the user back when the question itself is unclear.

North star

The problem, in one listing

In August 2026 a live marketplace listing advertised four pack sizes of bottled water in its title: 24 × 350 ml, 12 × 550 ml, 6 × 1.25 L and 2 × 9.5 L. The page held one price at a time, the price of the size selected. The headline price, 9.89, belonged to the 12 × 550 ml pack, not the 9.5 L carton a shopper might ask about. That price only appeared after clicking the size, and it read 16.15 one day and 17.95 two days later.

The page's machine-readable data, schema.org JSON-LD, said the same thing more firmly: one plain price of 9.89 that never changed when another size was chosen. Schema.org has AggregateOffer, with a low and a high price, for exactly this case. Neither that marketplace nor WebArena uses it.

A live AI shopping assistant, asked for the cheapest 9.5 L carton, named one seller as 27 per cent cheaper and worked out a cost per litre to back it up. It was wrong: for that size the seller was dearer. The answer carried no sign of doubt, and no merchant had done anything deceptive.

That is interaction-gated information: data that is on the page but only reachable through an interaction, where the agent's first look gives no hint that anything is missing. Sizes and colours are one form. Paginated reviews, stock by size, shipping cost by address and voucher rules are others.

Evidence

Markets and questions

The shop's own 104,368 products never change price by size, so every gated product here is ours. Each market is a file generated from a seed, seeded into the shop, and checked against the rules that make its questions a real test.

How a market is made

A generator draws a whole market from a random seed: fifteen sellers, their sizes, their prices and their stock. It then tests the draw against a list of rules, such as "the cheapest advertised listing is not the right answer" and "the listing that looks cheapest for size M does not sell size M". If any rule fails it draws again, sometimes thousands of times. The accepted draw is written to env/fixtures/, and the question file with its answer key is written from that same file, so the two can never disagree.

env/seed_variants.py then creates each listing in Magento as a configurable product with one child per size, every SKU prefixed IGR-. For clothing, env/pick_apparel_market.py also checked where the answer actually rendered on the results page, because Magento orders results by how many sizes a listing has, not by catalogue order.

Why openJiuwen stops at four listings

openJiuwen's prompt tells it to use the smallest probe that fits, and on a listing page to call browser_probe_cards and trust what it returns. By default that probe reports only the cards inside the browser window. At 1200 × 701 the window holds one row of four cards, and nothing in the reply says eleven more exist (decision log, 14 September).

The question"which seller is cheapest for size M"
The promptsmallest probe first, trust the card probe
browser_probe_cardsviewport_only true by default
4 cards of 15one row, no sign of the rest
An answer from 4 listingsconfident, often wrong

The one-setting change behind cell 2

To test whether that default is the cause, cell 2 changes it and nothing else. The patch wraps the tool and sets viewport_only to false unless the agent passes a value of its own. It is switched on by an environment variable, so a run without the variable is untouched.

What the developers say about observation

openJiuwen's developer talk deck, slide 5, says the agent "reads the control tree (DOM + AX) by default & adds screenshots only when the page is ambiguous". On a gated listing the DOM and a screenshot agree with each other, because the price is missing rather than contradicted, so adding vision would not help. The harness paper, arXiv 2608.27969, is about coding agents and makes no claim about browsing.

openJiuwen already has an ask_user tool and a page state that tracks which fields it has covered. The box connects that coverage to the question being asked.

How the theme gates the price

Stock Magento sends every size's price with the first page load and prints each surcharge in the size menu, so nothing is really gated. The theme sets every price in that table to the price already in the price box, so no label shows a difference. The real prices travel separately and are written into the price box only for the size actually chosen, 60 milliseconds after it changes.

It is selected by the browser's user agent, so ordinary browsing, and every run recorded before the theme existed, sees the shop exactly as before.

The 60 ms delay stops Magento's own widget from overwriting the real price. One agent-written script read the price before it, see Results.
