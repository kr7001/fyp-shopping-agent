The headline: the agent reading only four listings of fifteen is caused by one default setting in the browser agent we build on. Turning that setting off takes it from meeting the evidence standard in 3 runs out of 15 to 15 out of 15. A second agent I wrote from scratch, which has no such setting, reaches 12 of 15 without being told anything.

That is a smaller claim than "AI shopping agents under retrieve", and a much better supported one. It is a named, reproducible defect in a production agent, shown three different ways.

1. Where we left off, and the two problems in the way

At the last meeting the project had a result it could not fully trust, because two things in the setup were doing work that should have been done by the agent.

The two problems

2. Solved: the shop no longer gives prices away

1

What was wrong. Magento, the shop software, sends the browser every size's price when the page loads, and the menu then writes each one as a surcharge.

So an agent could read $16.14 from the page, add $32.50 from the label, and report $48.64 without ever selecting the size. Which is exactly what it did: across 290 stored answers, 48 showed the agent adding a surcharge instead of clicking.

2

What I built. A replacement page template that flattens the price table the shop hands the browser, so every size reports the same starting price and no label can show a difference. The real prices travel hidden, and are written into the price box only for the size actually chosen.

3

How I know it worked. The shop serves this version only to a browser that identifies itself a certain way, so ordinary browsing and every run recorded before it are untouched. That let me run the same twelve runs twice, changing only the menu.

Twelve runs each, the size menu being the only difference
Shop versionClicked a sizeAdded up the menu insteadWork doneCorrect
Prices shown in the menu0 of 124 of 1210.2 actions3 of 12
Prices hidden8 of 120 of 1218.3 actions2 of 12

The agent went from never clicking a size to clicking in two runs out of three, and stopped doing menu arithmetic entirely. It works 64 per cent harder and is no more correct, which is itself the point: the information really was gated, and retrieving it properly is expensive.

Where it is not airtight, stated plainly. The true prices are still inside the page, encoded. An agent that ran its own JavaScript could decode them without clicking. That mirrors the live marketplace, where an agent could call the same API the page calls, so it is a limitation of the setting rather than a defect. It is written down as a limitation rather than hidden.

3. Solved: why the agent only saw 4 listings of 15

This is the question you pushed on, and the answer took three attempts to get right. I was wrong twice along the way and both corrections are recorded.

1

First, the thing everyone assumes is wrong. The agent does read the page properly. It is not working from screenshots. Across 360 recorded runs it read the page structure 1,656 times and took only 277 screenshots, roughly thirteen to one.

2

The page is complete too. All fifteen products are in it. I measured them on one page load.

So where do the other eleven go? The agent has a tool that summarises the products on a page. That tool has a setting, on by default, that throws away anything below the bottom of the window. It finds all fifteen, then discards eleven.

And the reply it sends back never says anything was dropped. I checked every field. It reports four and stops. The agent asks a fair question, gets an answer with no hole in it, and moves on.

4

The part that surprised me. You would assume the summary exists to save money. It does the opposite.

The tool called compact is nearly three times larger than the thing it summarises, and names a quarter as many products. A quarter of its bulk is long technical addresses for each element. Whatever preferring it saves, it is not tokens.

5

How I fixed it, and why it is a fair test. I did not edit their code. I wrote a small patch in our own repository that flips that one setting and changes nothing else: same instructions, same tools, same model, same budget, same shop. The agent is never told about the change.

That matters because if I had also reworded the prompt, any difference could be the wording. One setting, one difference, one explanation. The result is in section 6.

One thing I will not claim. openJiuwen's public talk says the agent reads the page by default and uses screenshots only when the page is unclear. That claim is true. I said otherwise at one point and was wrong. The problem is not that they avoid reading the page. It is that their summarising tool quietly drops most of it and does not say so.

4. New product category: fifteen clothing listings

Everything until now was bottled water, so every number was a number about one product type. This is the second category, and it adds a kind of gating water does not have.

The three states a size can be in

Why this market is different from the water one
StateListingsWhat the shopper sees
Sells size M and can ship it5A normal, selectable option
Sells size M and has none left5The size is listed but greyed out and cannot be chosen, so its price is unreachable
Never sold size M5The size is simply absent, and nothing marks the absence

The middle state is the one real marketplaces have and our shop could not previously render. Shopee shows a sold out size as a greyed button, Lazada as a greyed tile, and neither publishes its price. Getting our shop to do the same took one configuration change plus creating the stock with zero quantity.

The question, and the three ways to get it wrong

How the market is generated, and why not by hand

The market is drawn at random, checked against thirteen properties, and thrown away if it fails any of them. Roughly one draw in 1,900 passes, so the generator tries up to 80,000 times. Seed 203 was accepted on attempt 590.

Why it has to work this way: a market written by hand would be written by someone who already knows what the agent gets wrong, and would flatter or punish it by accident. A market drawn at random and then filtered can only pass if it has the properties written down in advance.

The thirteen rules, grouped by the objection each one answers
GroupRulesWhat a sceptic could otherwise say
The answer is unambiguousexactly one winner, and it beats the runner up by at least 8 per cent"The agent was nearly right, you are splitting hairs"
A glance is actively wrongthe cheapest advertised listing is not the winner, the cheapest of all does not sell the size, the lowest listed price for the size cannot be shipped, and four different sellers answer four different questions"The agent could have guessed from the search page and been right"
The work is realat least 3 listings can be ruled out without opening, at least 8 must be opened"It was answerable by opening one or two"
All three states are well populatedat least 4 never sell it, at least 3 are sold out, at least 4 can ship it"Sold out listings are a curiosity, not a real case"

Two rules I had to delete, which is worth a sentence. Two of them tried to control where a listing appears on the results page, by controlling its position in the catalogue. That does not work. What actually decides page position is how many sizes a listing sells, because the shop's search index counts every size separately. Eight seeds in a row were rejected before I measured this. The generator now makes no claim about position, and position is measured on the real rendered page after seeding instead.

Everything above was checked against the live shop before any run: all fifteen listings opened in a browser and compared to the specification on price, sizes offered, sizes greyed out, and price leaks. All fifteen agree. All six answers were then re-derived by browsing the shop rather than read from the file. All six match.

5. The second agent, and what it is for

This is the part worth going slowly on, because it is what makes the whole result trustworthy.

The problem it solves

Every failure measured so far came from one agent. So a reasonable person asks: is this a fact about AI shopping agents, or a fact about this particular piece of software?

You cannot answer that from inside one agent, however many times you run it. You need a second one that shares the model and shares nothing else.

What it is, concretely

A browsing loop I wrote from scratch, about 370 lines. It drives a real browser and has exactly four tools:

Its entire toolset
ToolWhat it does
gotoGo to a web address and return the page's text
read_pageReturn the text of the page it is on
select_optionChoose a value in a dropdown, then return the page text
finishGive the final answer

And this is its entire instruction, 328 characters. openJiuwen's equivalent file is 17,937 characters.

The sentence that matters is "nothing here tells you how much to look, because how much to look is your decision". That is deliberate. How much to look is the thing being measured, so the agent must not be told.

How it differs from openJiuwen, and why each difference is there

What differs, on purpose

So the two agents differ in their tooling and their instructions, and in nothing else. If both fail the same way, the failure belongs to the model and the claim is about AI shopping agents generally. If only openJiuwen fails, the claim is about openJiuwen.

A bug in it I found and fixed, reported because it voided results

The second agent's first twelve runs are void and are not cited anywhere. It reads pages as plain text, which does not say where a link goes, so it is also given a list of the page's links. That list was capped at 80, collected in page order, and this shop puts its menus and account links before the products. All eighty slots went to navigation and not one product address was ever shown. The agent guessed addresses from product names, and this shop addresses products by code, so every guess hit a missing page. Across those twelve runs: zero product pages opened, 49 missing page errors.

The fix lists content links first and gives navigation a small allowance. Verified afterwards: fifteen product links offered, the first at position three, following it loads a real product page, and a sold out size shows as unavailable in its view. It was then re-run, and that re-run is cell 3 below.

I report this because a figure from those runs had already been given to you: that the plain loop opens 3.7 listings against openJiuwen's 5.7. That figure counted missing-page errors as listings. The real count was zero. It has been withdrawn.

This makes the claim smaller, and much better evidenced

Not: "AI shopping agents under retrieve on pages with hidden information." But: "openJiuwen's card summary filters to the browser window by default and does not report what it dropped. On a fifteen listing market that costs it eleven listings, and it meets the evidence standard in 3 runs of 15. Removing that one setting raises it to 15 of 15. A second agent without that setting reaches 12 of 15 unprompted." It could have gone the other way. Had the plain loop also stopped at four, the claim would have been the bigger one. It did not, so the honest finding is the smaller one.

Two things I did not expect

COST

The second agent is the cheapest

Same accuracy as repaired openJiuwen for 27 per cent of the cost, $2.00 against $7.38. openJiuwen's expensive path is expensive because its unfiltered summary is 88,822 characters where the plain page structure is 11,394, re-sent at every step.

WHAT STILL FAILS

The remaining errors moved

Once both agents could see everything, every wrong answer was either the advertised price used as the size's price, or offered confused with buyable. Neither is about how much it looked. The failure moved onto exactly the gate the clothing market was built to create.

The sharpest single example. Asked "what is the lowest price anyone charges for size M that can be bought", the second agent answered $25.77, correctly, three times out of three. Asked "which seller is cheapest for size M, counting only listings that can supply it", the same agent on the same market answered Copperfield at $23.40, three times out of three. It holds the right figure and the wrong seller at the same time. That is not a retrieval failure at all, and it is what the next phase has to address.
