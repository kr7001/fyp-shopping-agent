1. The shop shortcut, and whether it is really fixed

First, which shortcut. There are two completely different ones in this project and they have been muddled in conversation, including by me.

Two shortcuts, two different stories
ShortcutWhat it isState
A. The shop published variant pricesMagento put every size's price in the page on load and wrote the extra cost into each menu option, so the agent could do arithmetic instead of clicking a sizeFIXED, MEASURED
B. The agent reads four listings of fifteenThe card summary reports only what is on screen, so the agent treats four products as the whole marketNOT FIXED

When I said "solved", I meant A. B has never been fixed and I have never claimed it was. B is the subject of the project, not a bug to be patched, and the open question is whether its cause is the tool or the model.

What was built for A

A replacement page template that the shop serves only to a browser identifying itself as IGRGated. Ordinary browsing and every run recorded before it are untouched. It does two things to the block of data Magento sends the browser.

The evidence that it worked

Measured on 18 September on the same product page, changing only which browser identity was used.

And the behaviour change it produced, twelve runs each, the menu being the only difference: the agent went from choosing a size in 0 of 12 runs to 8 of 12, worked 64 per cent harder, and was no more right. It stopped doing arithmetic on the menu in all twelve.

Why I will not say it is fixed completely

So the honest sentence is: the leak that mattered is closed and the closing was measured, the mechanism has a known decodable back door that mirrors the real marketplace, and the live state needs one check before the next run.

3. Does openJiuwen use the DOM tree

Yes. It reads the DOM and it reads accessibility information. What I told you earlier was wrong, and this section shows the code.

Your follow up is the right one: if it reads the DOM, how can it see only four listings? The answer is that reading the whole page and reporting the whole page are two different steps, and the code does the first then undoes it.

It reads the page

The card summary is a piece of JavaScript that openJiuwen sends into the browser to run inside the page. These lines are from that script.

Line 203 asks the live page for every matching element, which is reading the DOM. Lines 160 and 277 read role and aria-disabled, which are accessibility attributes. So the summary is built out of both the DOM and accessibility information.

So both things are true at once, and they are not in conflict. It reads the entire DOM. Then it discards every element sitting below the bottom of the window, and the reply it returns never mentions that anything was discarded. Our product cards start 671 pixels down the page and the second row starts at 1128, in a window 701 tall, so everything from the second row onward fails that one test.

Proved by running their code both ways

On 18 September I loaded openJiuwen's own summary script out of its repository and ran it against our shop twice, changing only that one setting and nothing else.

For comparison the accessibility tree of the same page is 11,394 characters and names all fifteen. So the summary the agent is told to prefer is nearly three times the size of the accessibility tree and names a quarter as many products. Whatever preferring it saves, it is not tokens.

The correction, stated plainly: openJiuwen's claim that it reads the control tree by default is true. The four listing behaviour is not caused by avoiding the DOM. It is caused by a geometry filter inside a summarising tool, and by that tool not reporting what it dropped.

What is still not proven. Whether that filter causes the agent to stop at four, or whether a model inclined to look less would stop there anyway. Across unmodified runs, 74 opened exactly four listings and not one of those had read the search page in full, against 30 of 38 that opened some other number. That is a strong association and it is not a controlled test. The experiment that settles it is in section 5.

4. The second agent, and why its runs are void

It exists, its design is sound, and every run it has produced is unusable. I found that today while checking this answer rather than asserting it. The cause is a bug in code I wrote.

What it is

A browsing loop written from scratch in experiments/naive_agent.py, deliberately plain. It exists to answer one question: is the four listing behaviour a property of agents, or a property of openJiuwen's summarising tool. If a loop with no such tool still stops early, the behaviour belongs to the model.

The two agents side by side
PropertyopenJiuwenThe plain loop
ToolsAround two dozen, including navigate, click, type, snapshot, screenshot, run code, and its own card summary and interactive probesFour. Go to a web address, read the page, choose a dropdown option, answer
InstructionsA long built in prompt. The browser prompt file is 17,937 characters, and it tells the agent which tool to prefer and to use the summary as its evidence rather than taking snapshots328 characters, and the operative sentence is "Nothing here tells you how much to look, because how much to look is your decision"
What it sees on arrivalA filename. The page content is written to disk and the agent is given its name, so it must then ask for somethingThe page text immediately, every time, with no asking
Window limitYes, on the summary, on by defaultNone. It reads the whole page regardless of what is on screen
Held constant on purposeSame model, same step budget of 100 tool calls, same window size of 1200 by 701, same scoring, and both emit a Page URL: line so one counter measures both

What went wrong

The loop reads the page as plain text, which does not tell you where a link goes. So it is also given a list of links. That list is capped:

That comment is wrong, and the links are collected in the order they appear in the page. The shop's header, category menu and account links come first. Checking a real run's observation: 80 links were listed and not one of them was a product. The last few were category pages like "Sports and Outdoors, Fan Shop, Footwear".

So the agent was never shown a single product address. It guessed them from the product names, and the guesses were wrong, because the shop addresses these products by their code rather than their name. The real address is /igr-cal-01.html and the agent tried /calderwood-still-spring-water-multipack-kettering-distributors.html.

It answered questions about the price of a pack size while never once having seen a page that contains a pack size. Any score from these runs measures guessing, not retrieval.

This also corrects a published figure. I reported that the plain loop opens 3.7 listings against openJiuwen's 5.7, and called it a result that falsified my own prediction. The counter that produced 3.7 recognises a product page by the shape of its address, and the missing page it was served has the same shape. So 3.7 is a count of error pages. The real figure is zero, and the comparison does not exist.

To your question of whether the comparison is invalid because of openJiuwen's four listing problem: no, that is not the reason. A comparison between an agent that reads four listings and an agent that reads all of them would be a perfectly good experiment, and is one I want. It is invalid because the second agent never reached a listing at all.

The fix is one line, raising or removing the link cap, plus putting product links first. It costs nothing. Until it is fixed and re-run, this project has one agent, not two, and the external validity question is open.

What makes it controlled, where the old batches were not. Every cell is the same six questions, the same market fingerprint, the same shop, the same model, the same window and the same budget. The only thing that changes between cells is the one named in its row. Earlier batches changed the market, the shop and the agent at the same time, which is why they cannot be read against each other.

Reviews are deliberately left out. Nine questions exist and have never been run, and page turning makes them the most expensive and least predictable arm. They belong after the matrix, not inside it.
