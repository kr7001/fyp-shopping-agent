When I said "solved", I meant A. B was not fixed and I have never claimed it was. B is the subject of the project rather than a bug to be patched.

What has changed since this was written: the open question in B, whether the cause is the tool or the model, is now answered. It is the tool, and the evidence is in section 7. 3. Does openJiuwen use the DOM tree

Yes. It reads the DOM and it reads accessibility information. What I told you earlier was wrong, and this section shows the code.

Your follow up is the right one: if it reads the DOM, how can it see only four listings? The answer is that reading the whole page and reporting the whole page are two different steps, and the code does the first then undoes it.

It reads the page

The card summary is a piece of JavaScript that openJiuwen sends into the browser to run inside the page. These lines are from that script.

Line 203 asks the live page for every matching element, which is reading the DOM. Lines 160 and 277 read role and aria-disabled, which are accessibility attributes. So the summary is built out of both the DOM and accessibility information.

This is the part that resolves your question. The script finds elements first, and filters them afterwards. Here is the loop, in order:

And isVisible contains the test that does the damage. The card summary has its own copy of it at lines 670 to 688.

So both things are true at once, and they are not in conflict. It reads the entire DOM. Then it discards every element sitting below the bottom of the window, and the reply it returns never mentions that anything was discarded. Our product cards start 671 pixels down the page and the second row starts at 1128, in a window 701 tall, so everything from the second row onward fails that one test.

Proved by running their code both ways

For comparison the accessibility tree of the same page is 11,394 characters and names all fifteen. So the summary the agent is told to prefer is nearly three times the size of the accessibility tree and names a quarter as many products. Whatever preferring it saves, it is not tokens.

The correction, stated plainly: openJiuwen's claim that it reads the control tree by default is true. The four listing behaviour is not caused by avoiding the DOM. It is caused by a geometry filter inside a summarising tool, and by that tool not reporting what it dropped.

What is still not proven. Whether that filter causes the agent to stop at four, or whether a model inclined to look less would stop there anyway. Across unmodified runs, 74 opened exactly four listings and not one of those had read the search page in full, against 30 of 38 that opened some other number. That is a strong association and it is not a controlled test. The experiment that settles it is in section 5.

4. The second agent, and why its first runs were void

It exists, its design is sound, and every run it has produced is unusable. I found that today while checking this answer rather than asserting it. The cause is a bug in code I wrote.

What it is

A browsing loop written from scratch in experiments/naive_agent.py, deliberately plain. It exists to answer one question: is the four listing behaviour a property of agents, or a property of openJiuwen's summarising tool. If a loop with no such tool still stops early, the behaviour belongs to the model.

5. How the markets are generated

The markets are not written by hand. A market is drawn at random, checked against a list of properties, and thrown away if it fails any of them. That is rejection sampling, and it is the reason a market can be trusted to test what it claims to test.

Why it has to work this way: a market written by hand would be written by someone who already knows what the agent does wrong, and would flatter or punish it by accident. A market drawn at random and then filtered can only pass if it has the properties stated in advance, and those properties are in the file before any run.

A clean five, five and five. The thirteen rules together are satisfied by roughly one draw in 1,900, which is why the generator tries up to 80,000 times per seed and why these markets cannot be written by hand. Most of the properties fight each other.

Two rules that were removed, and why that matters

There were fifteen. Two required the winner to sit late in the catalogue and the cheapest advertised listing to sit early, as a way of keeping the answer off the first screen and the trap on it. Both were written against the listing's position in the catalogue, and catalogue position does not decide where a listing renders.

What does, measured across eight generated markets: the number of sizes a listing sells. Magento indexes every child product, so a listing offering four sizes carries the brand name four times in the search index and outranks one offering two. In the market measured, every listing rendering in cards 1 to 8 had four sizes and cards 13 to 15 had two.

That made the rule unsatisfiable rather than strict. The trap is by construction a listing missing a size, so it has fewer sizes, so it renders late. Eight consecutive seeds were rejected with the trap at cards 8, 12, 8, 14, 10, 15, 12 and 13, never once in the first four. Requiring the trap to carry all four sizes instead drops the acceptance rate from 1 in 1,900 to 1 in 40,000, because it contradicts what makes it a trap.

So the generator stopped claiming anything about position, and position is now measured on the rendered page after seeding. A draw is kept only if the answer renders outside the first row and something inside the first row advertises below it. Seed 203 passed: the answer renders at card 12, and three of the first four cards advertise below $25.77.

Why "by question". Each cell asked the same five gated questions three times, and the questions differ hugely in difficulty. Every cell answered all-stocked correctly every time. Almost nothing answered count-stocked correctly. Pooling treats an easy question and a hard one as the same thing. Comparing within each question first and then combining removes that. It is the standard exact test for this layout, and it is used because of the layout, not because of the answer it gives. Both columns are shown so you can see the difference.

The mechanism result is stronger than I said. With the scoring error fixed, removing the window limit raised accuracy from 4 of 15 to 11 of 15. That holds under either test, p 0.027 pooled and 0.005 by question. On 7 October I called it suggestive. It is now a result.

The second agent result is weaker than I said. Its fifteen gated runs are seven different runs, because it samples at temperature zero and replays itself exactly. Counted honestly it still opens more than openJiuwen as shipped, at p 0.031, but that is one comparison near the line, not "settled".

openJiuwen's card summary filters to the browser window by default and does not report what it dropped. On a fifteen listing market it opens what the answer needs in 3 runs of 15. Removing that one filter raises this to 15 of 15, and raises accuracy from 4 to 11 of 15. A second agent with no such filter opens the whole market without being told to. The failure is this tool's default, not the model's inclination. The claim as it now stands. One market, one model. The middle sentence is the strong one.

What the fix costs

Lifting the limit costs 2.7 times as much, because the summary grows from four cards to fifteen and is re-sent at every step. That is the argument for a retrieval policy rather than a bigger window: the aim is cell two's accuracy at something closer to cell one's bill. Costs are the provider's own charge per call, and section 8 shows they match the account to the cent.

Honest limits on this result. One market, one model. The second agent's evidence is seven runs, not fifteen. The two agents sample differently, 0.2 against 0, and only openJiuwen has a ten minute clock limit, which section 8 explains. The gated shop reveals a price 60 milliseconds after a size changes, which decided one run. Two of the five gated questions turn on an ambiguous word. None of these touch the cell 1 against cell 2 comparison, which is the same agent with one setting changed.

Wrong 1: a scoring error

Cell 2, count-buyable, run 3. The question asks how many listings have size M in stock. The answer is 5. The run said:

"After checking all 15 Thornwood Heavyweight Cotton Tee listings on the search results page, I found that 5 products have size M in stock and available to buy right now." Correct. The scorer marked it wrong.

The scorer took the first number in the answer as the count, which here is the 15 from "all 15". I then described this run to you as "counted 15, ignoring availability entirely". That was wrong twice over. The scorer now skips numbers that say how many were looked at, "all 15", "of the 15", "out of 15", and the digits inside prices. Ten test phrasings pass. Re-scoring every run on this market with the fix changes exactly this one verdict. The old verdicts are kept beside the new ones in each suite file, so the change is visible.

Not wrong, but ambiguous: the word "offer"

Two questions use it. "Does every listing offer size M" and "how many listings offer size M". The answer key, fixed before any run, counts a sold out size as offered, because it is still on the menu. So the count is 10. Every run that explained its count read "offer" as "can sell it now", which makes the count 5. One run answered 10 without saying why. The clearest evidence is a cell 2 run that got every fact right and still answered 5:

What went wrong while it ran: the laptop went to sleep

The batch started at 03:44 on battery, and the machine slept, waking only briefly, until about 07:44. From then until 08:29 it ran in short bursts, about 45 seconds awake and 8 asleep, and the runs in that window came through with normal timing and no errors. It slept again from 08:29 until the power button was pressed at 09:41. The system's own power log records every sleep and wake. Three runs were caught in it. openJiuwen's ten minute clock kept counting while the machine slept, so two of them were stopped as "exceeded 600s" having used only 74 and 54 of their 100 steps. One finished after waking.

The rule for leaving a run out has to be objective, so it is this: a run whose log goes silent for more than 60 seconds was suspended, and is void. openJiuwen logs a heartbeat every 30 seconds while a run is alive.
